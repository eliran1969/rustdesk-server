# Web Console לשרת RustDesk - מסמך תכנון

תאריך: 2026-11-14
קטלוג הפיצ'רים המלא (מקור האמת לכל מסך, שדה וכלל): `docs/webconsole/feature-catalog.md`

---

## 1. מה ולמה

**מה:** גרסה משלך ל-Web Console של RustDesk Server Pro: אתר ניהול בדפדפן ו-REST API בפורט 21114, בתוך עותק משלך של שרת RustDesk. המנהל מתחבר, רואה את כל המחשבים בזמן אמת, ומנהל משתמשים, קבוצות, פנקסי כתובות, מדיניות, הרשאות ויומנים.

**למה:** השרת החינמי של RustDesk (hbbs/hbbr) מחבר בין מחשבים, אבל אין בו ניהול. ה-client (הספרייה `eliran1969/rustdesk`) כבר מכיל את כל צד ה-client של הניהול: דיווח מכשירים, יומנים, פנקס כתובות, כניסה, מדיניות וניתוק מרחוק. חסר רק שרת שעונה לו.

**עיקרון מנחה:** זהות פונקציונלית למקור, כפי שמתואר בתיעוד הרשמי. אותם מסכים, שדות, כללים ו-API, כך שה-client הקיים והסקריפטים ב-`res/*.py` יעבדו מולו בלי שינוי.

## 2. מטרות, לא-מטרות, אנטי-מטרות

**מטרות**
- כיסוי של כל פיצ'רי ה-Console שבקטלוג, בשישה שלבים (סעיף 6).
- תאימות API מלאה ל-client הקיים ולסקריפטים ב-`res/*.py` (אותם נתיבים, שדות ותשובות).
- שרת אחד שמותקן כמו השרת הרגיל (קובץ בינארי או Docker), עם הממשק מוטמע בתוכו.
- כל שלב שמסתיים הוא מערכת עובדת ושמישה, לא חצי עבודה.

**לא-מטרות**
- רישיונות. רלוונטי רק למוצר המסחרי.
- Custom Client Generator (בניית client ממותג בענן). פרויקט נפרד אחרי שלב 6.
- web client (`/web`) ו-WebSocket. קיימים כבר בנפרד, לא חלק מה-Console.
- שינויים ב-client, למעט אם יתגלה באג או חוסר בתאימות.

**אנטי-מטרות (כישלון גם אם "עובד")**
- ה-client הקיים לא מצליח להתחבר, לדווח או להתחבר למשתמש מול השרת.
- פרצת אבטחה: סיסמאות לא מוצפנות, API בלי הרשאות, משתמש רגיל שרואה נתונים של אחרים, או סיסמאות של פנקס כתובות שחוזרות בממשק.
- שבירה של hbbs/hbbr: חיבור בין מחשבים שהפסיק לעבוד, או נהיה איטי, בגלל ה-Console.
- fork שאי אפשר לעדכן מ-upstream כי השינויים מפוזרים בכל הקוד.

## 3. אילוצים

- **בסיס קוד:** fork של `rustdesk/rustdesk-server` (Rust, edition 2021). כבר יש בו `axum 0.5`, `sqlx 0.6` (SQLite), `bcrypt`, `jsonwebtoken`, `tower-http`, ומסד `db_v2.sqlite3` עם טבלת `peer`.
- **רישיון AGPL-3.0:** מותר לשימוש ולשינוי. אם השרת מוצע כשירות לאחרים, חובה לפרסם את הקוד ששונה.
- **פורטים:** 21114 (Console/API), בנוסף ל-21115 עד 21119 הקיימים.
- **ה-client קובע את החוזה:** נתיבים, שדות JSON ותשובות טקסט (`SYSINFO_UPDATED`, `ID_NOT_FOUND`) חייבים להתאים לקוד ב-`src/hbbs_http/`, ‏`src/server/connection.rs` ו-`flutter/lib/models/`.
- **ה-client מסנן מפתחות רגישים ממדיניות** (`BLOCKED_CONFIG_OPTIONS` ב-`src/hbbs_http/sync.rs`). אין טעם לאפשר אותם בממשק.
- **עדכון מ-upstream:** כל הקוד החדש במודולים חדשים. שינויים בקבצים קיימים של hbbs מצומצמים לנקודות חיבור (hooks) קטנות.

## 5. ארכיטקטורה

### 5.1 מבנה
```
rustdesk-server (fork)
├── src/
│   ├── rendezvous_server.rs   ← קיים; רק hooks קטנים (שלב 5)
│   ├── relay_server.rs        ← קיים; ללא שינוי (שלב 6: health)
│   ├── main.rs                ← קיים; מפעיל גם את ה-Console
│   └── console/               ← חדש: כל ה-Console
│       ├── mod.rs             (הפעלת שרת HTTP ב-21114)
│       ├── db/                (migrations + שאילתות)
│       ├── auth/              (סיסמאות, sessions, tokens, 2FA, OIDC, LDAP)
│       ├── api/               (handlers לפי תחום: client, users, devices, ab, audits, strategies...)
│       ├── access.rs          (מנוע החלטות: בקרת גישה, control roles, admin roles)
│       └── web.rs             (הגשת הממשק המוטמע)
└── console-ui/                ← חדש: React + TypeScript + Vite; נבנה ומוטמע בבינארי
```

### 5.2 החלטות טכניות (החלטות שלי, ניתנות לשינוי)
- **שרת HTTP:** axum (כבר תלות). נשקול שדרוג גרסה אם 0.5 חוסם, בתנאי שזה לא מסבך merge מ-upstream.
- **מסד נתונים:** אותו קובץ SQLite של hbbs (`db_v2.sqlite3`), עם טבלאות חדשות ו-migrations מגורסים. טבלת `peer` הקיימת היא מקור האמת למכשיר (ID, uuid, pk), וטבלה חדשה מחזיקה מידע מורחב.
- **סיסמאות:** bcrypt. **Sessions:** טוקן אקראי שנשמר בטבלה (לא JWT), כדי לאפשר Force Logout מיידי.
- **ממשק:** React + TypeScript + Vite. ה-build מוטמע בבינארי (`include_dir` או `rust-embed`), כך שאין קבצים נפרדים להתקנה.
- **תקשורת Console↔hbbs:** אותו תהליך. hbbs שואל את מנוע ההחלטות (`console::access`) ישירות דרך פונקציה, ונתוני "מקוון/לא מקוון" נלקחים מזיכרון ה-PeerMap של hbbs.

### 5.3 נקודות חיבור ב-hbbs (שלב 5-6)
- `handle_punch_hole_request` ו-`RequestRelay` ב-`rendezvous_server.rs`: לפי `token` (המשתמש המחובר בצד השולט) ו-`id` (היעד), מנוע ההחלטות מחזיר אם החיבור מותר, ואם כן מצרף `control_permissions` לתשובה.
- `get_relay_server`: בחירת relay מקוון לפי GeoIP במקום סבב (שלב 6).

## 7. מה נשאר לבונה להחליט
- מבנה טבלאות מפורט ושמות.
- פורמט JSON מדויק במקומות שה-client והסקריפטים לא מגדירים אותו. גוזרים מהקוד, וכשאין מקור מחליטים ומתעדים.
- עיצוב ויזואלי של הממשק (פריסה, צבעים), בהשראת המבנה המקורי: תפריט צד עם Devices, Users, Groups, Device Groups, Strategies, Control Roles, Admin Roles, Address Books, Logs, Settings.
- אסטרטגיית בדיקות: בדיקות יחידה למנוע ההחלטות, בדיקות API, והרצת סקריפטי `res/*.py` כבדיקות תאימות.

## 8. החלטות שהתקבלו אחרי בדיקת הבונה (החלטות שלי, לבדיקת המשתמש)

1. **בקרת גישה כשאין חוקים או כשהשולט לא מחובר:** החוקים חלים רק כשהשולט מחובר (יש `token`) **וגם** המכשיר משויך למשתמש או לקבוצת מכשירים. בכל מקרה אחר החיבור ממשיך כמו היום, עם סיסמה של המכשיר, ו-Control Role "Not Logged" חל עליו. מכשיר או משתמש מושבת נחסם תמיד. בהגדרות נוסיף אופציה "לחייב כניסה כדי להתחבר" (כבויה כברירת מחדל). **למה:** כך שדרוג השרת לא שובר אף חיבור קיים (אנטי-מטרה), ומי שרוצה הקשחה מפעיל אותה במודע.
2. **HTTPS:** השרת מגיש HTTP רגיל ב-21114, ו-HTTPS מטופל ע"י reverse proxy (Nginx/Caddy) על 443, כמו במקור. ה-client עצמו מסיר `:21114` מכתובות https (`src/common.rs:1278`). נספק תיעוד ודוגמת הגדרה.
3. **EXE לפי שם קובץ (שלב 6):** השרת מגיש client רגיל (מקובץ שהמנהל מעלה, או מה-Release ב-GitHub שלך), עם שם קובץ שמקודדות בו ההגדרות, כמו במקור. בלי חתימה ובלי בנייה מחדש. זה לא Custom Client Generator.
4. **אימות סקריפטים לפני שלב 6:** בשלבים 2 עד 5 ה-API מקבל גם את טוקן ה-session של admin מחובר כ-`Authorization: Bearer`. בשלב 6 נוספים API Tokens עם הרשאות.
5. **גרסת פרוטוקול:** לפני שלב 1, מעדכנים את `hbb_common` בשרת לגרסה שה-client משתמש בה, כדי ששדות כמו `switch_code`, ‏`webrtc_sdp_offer`, ‏`control_permissions` ו-`ControlledContext` יהיו מוכרים.

## 9. החלטות המשתמש (אחרי בדיקת הבונה)

1. **שרת קיים:** יש שרת RustDesk פעיל ב-Docker על Synology. השרת החדש הוא **שדרוג במקום**: אותה תיקיית נתונים, אותו זוג מפתחות (`id_ed25519`, `id_ed25519.pub`) ואותו `db_v2.sqlite3`. migrations רק מוסיפים טבלאות ולא משנים או מוחקים את הקיים. לפני כל שדרוג: גיבוי אוטומטי של קובץ ה-DB. הפצה: Docker image (amd64, ולפי דגם ה-Synology גם arm64) עם docker-compose שמחליף את ה-hbbs הקיים ומוסיף את פורט 21114. בשלב 1 בודקים קודם על התקנת ניסוי עם עותק של הנתונים, ורק אחר כך על השרת האמיתי.
2. **שפת ממשק:** עברית ואנגלית מההתחלה. מערכת תרגום (i18n) עם מתג שפה, ותמיכה מלאה ב-RTL בעברית ו-LTR באנגלית (CSS logical properties, אייקונים כיווניים מתהפכים). כל מחרוזת בממשק עוברת דרך קובצי התרגום, ואין טקסט קשיח. אפשר להוסיף שפות בהמשך.
